VoiceJournal App Experience

These are the pre-implementation wireframes for the full VoiceJournal desktop experience. They were shaped through four subagent-backed iterations plus official platform guidance from Apple Human Interface Guidelines, Microsoft Windows app design guidance, and GNOME HIG. The goal is one product that still feels premium and native on macOS, Windows, and Linux.

Internet Research Applied

Apple HIG

  • Keep toolbars sparse and grouped into a small number of functional sections.
  • Use one obvious trailing primary action, not multiple competing tinted actions.
  • Use standard back and close symbols.
  • Do not title windows with the app name when the content title is more useful.
  • Toolbar controls and window chrome should feel system-native, not custom-framed.

Microsoft Windows

  • Keep command locations consistent across pages.
  • Use a title bar plus clear command surface pattern for premium desktop feel.
  • Use adaptive content margins: generous on wider windows.
  • Top-level navigation should stay shallow and readable.
  • Overflow is acceptable, but the most important commands stay visible.

GNOME HIG

  • Header bars should align controls left, center, and right.
  • Keep only a small number of controls visible in the header bar.
  • Preserve blank drag space.
  • Prefer flat header-bar controls over heavy bordered button chrome.
  • Update header-bar controls by context, not by dumping every action into one row.

Four Iterations

Iteration 1

Baseline information architecture

  • Lock the core flow: Home → Session → Review → Save.
  • Make the header the action zone on every screen.
  • Keep Session centered around one trust-critical focal point.
  • Treat Settings as one tabbed modal, not its own navigation stack.
Baseline hierarchy Primary actions Low-fidelity layout

Iteration 2

Native premium correction

  • Reduce toolbar density and honor platform command placement.
  • Separate what changes by OS from what remains invariant.
  • Keep the body layouts stable while adapting the chrome.
  • Preserve one primary CTA and move secondary actions to overflow/contextual surfaces.
macOS unified toolbar Windows command surface GNOME header bar

Iteration 3

Premium reflective writing feel

  • Increase breathing room and emotional pacing.
  • Shift from procedural-looking UI to a calmer editorial hierarchy.
  • Make Review and Viewer feel like reading spaces, not utility panels.
  • Reduce clutter that makes the product feel commodity-grade.
Negative space Journal typography Calm interaction

Iteration 4

Feasibility and realism pass

  • Keep the final wireframes implementable in PySide6.
  • Respect the strict swipe contract, save-intent capture, and model-state gating.
  • Preserve accessibility and native-fit rules as non-negotiable.
  • Cut premium ideas that would create implementation drag without visible payoff.

Final Design Rules Before Implementation

Invariant Rules

  • Home, Session, Review, Viewer, and Settings keep the same body structure across all OSes.
  • Only chrome placement and header density change by platform.
  • `Cmd/Ctrl+N` must route through `NewEntryButton.activate()`.
  • `Cmd/Ctrl+S` must use the same save action path as the Review toolbar button.
  • Session trust cues are redundant by design and may not be simplified away in implementation.

Premium Rules

  • One primary action per screen, visually separated from utility actions.
  • More whitespace, fewer header controls, higher reading comfort.
  • Editing surfaces should feel deliberate and calm, not chat-app-like.
  • Archive screens should feel quiet; active voice screens should feel focused, not loud.
  • Do not add decorative complexity that fights the native chrome.

Feasibility Rules

  • Keep unified toolbars implementable with real `QToolBar` instances.
  • Respect the strict macOS swipe thresholds and momentum suppression.
  • Keep photo add as a dedicated inline Session action, not an overlay or modal interruption.
  • Keep save-intent capture explicit in Review state handling.
  • Prove bundled asset loading and re-pin the Gemma 4 E2B default load floor plus minimum supported RAM guidance before calling the release ready.
